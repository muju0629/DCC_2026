## 우리가 푸는 문제

**전화대화 음성 및 전사 데이터를 이용한 응급상황 인식**

> 목표: 음성 및 전사 등 발화 분야 내 광범위한 기술 스택을 이용하여 사회안전이라는 문제를 해결함.

119 신고 전화가 걸려오면 접수요원은 몇십 초 안에 상황을 파악하고 출동 자원을 배분해야 한다. 이 판단을 AI가 보조할 수 있으면 골든타임이 확보된다. 예선은 그 보조 시스템을 이루는 세 조각을 각각 만들어보는 과제다.

**데이터**: AI Hub "위급상황 음성/음향(고도화) - 119 지능형 신고접수 음성 인식 데이터"
서울·인천·광주 소방본부 실제 신고접수 음성 3,064시간 + 1:1 매칭 전사 158,973건. 단, **예선에서 학습에 쓸 수 있는 건 서울 데이터만** (104,496건).

### 세 미션

| | 과제 | 입력 | 출력 | 지표 |
|---|---|---|---|---|
| **Mission 1** | 신고자 성별 분류 | 음성 (원천데이터) | `gender` 남/여 | Accuracy |
| **Mission 2** | 신고자 / 119대원 분류 | 한 사람의 한 발화 조각 | `speaker` 0=수보자 / 1=신고자 | Accuracy |
| **Mission 3** | 환자 증상 인식 | 대화 전사 텍스트 | `symptom` 9종 멀티라벨 | 증상별 F1 계산 후 평균 |

**예선 최종 순위 = 세 미션의 평가 순위를 합산.** 한 미션을 버릴 수 없다.

미션별 입력 제약이 빡빡하다.

- Mission 1: 라벨링데이터 중 학습 때는 `startAt`, `endAt`, `speaker`만. **추론 때는 `startAt`, `endAt`만** (speaker 사용 불가)
- Mission 2: `startAt`, `endAt` 외 annotation 전부 금지. **`text` 사용 불가, 발화 순서(홀짝 등) 사용 불가**
- Mission 3: **전사 텍스트 외 라벨링데이터 사용 불가**. 9개 타깃 밖 symptom은 라벨에서만 제거(샘플은 유지)

공통 조건: AI Hub 데이터만 사용(외부 데이터 금지), 공개 오픈소스 pre-trained 허용, 상용 AI API(GPT-4o 등) 금지, Validation 폴더는 학습 금지, 샘플마다 label에 따라 다른 전처리 금지.

### 이 EDA가 답하려는 것

세 미션이 서로 다른 입력을 쓰기 때문에, "데이터가 어떻게 생겼나"를 한 번에 훑는 것으로는 부족하다. 미션별로 **무엇이 성능 상한을 정하는가**를 각각 찾는 게 목적이다.

| 섹션 | 답하려는 질문 |
|---|---|
| 0. 무결성 | 라벨과 오디오가 믿을 만한가. 타임스탬프로 잘라도 되는가 |
| 1. 오디오 포맷 | 사전학습 음성모델을 그대로 쓸 수 있는가. 무엇을 고쳐야 하는가 |
| 2. 발화 커버리지 | 110GB를 어떻게 감당할 것인가 |
| 3. Mission 1 | 넘어야 할 baseline은 몇 %인가. 라벨 단위가 무엇인가 |
| 4. Mission 2 | 어디서 점수를 잃게 되는가. 왜 순서를 금지했는가 |
| 5. Mission 3 | 무엇을 최적화해야 순위가 오르는가. 성능 상한은 어디인가 |
| 6. 텍스트 품질 | 어떤 언어모델이 이 데이터에 맞는가 |

## 1. 오디오 포맷 — 가장 먼저 반영해야 할 사실

```
channels=1  rate=8000Hz  width=16bit   → 100/100
통화 길이: 최소 30,120ms / 중앙 59,760ms / 최대 163,800ms
파일당 평균 1.07MB
```

**8kHz mono.** 여기서 파생되는 것:

1. **Wav2Vec2 / HuBERT / AST는 전부 16kHz 전제.** 8k를 그대로 넣으면 조용히 성능이 무너진다. `torchaudio.transforms.Resample(8000, 16000)` 필수.
2. **Nyquist가 4kHz.** Mel filterbank의 `f_max`를 4000으로 잡아야 한다. 기본값(sr/2 = 8000 가정)을 쓰면 위쪽 절반이 전부 빈 밴드가 되고, Mel-spectrogram을 2D 이미지로 넘기는 경로(ResNet/ViT)에서 입력의 절반이 낭비된다.
3. **mono라 채널 분리가 불가능.** Mission 2를 "수보자는 L, 신고자는 R" 식으로 푸는 지름길은 없다.
4. 성별(Mission 1)은 F0가 85~255Hz라 8kHz에서도 충분히 살아있다. 고주파 손실이 문제되는 쪽은 오히려 화자 구분이다.

**용량**: 서울 104,496건 × 1.07MB ≈ 110GB. AI Hub 표기 87.29GB는 압축 기준으로 보인다. 어느 쪽이든 Colab의 Drive에 통째로 못 올린다.

## 2. 발화 구간 커버리지 — 앞서 세운 용량 계획 수정

```
전체 111.6분 / 발화합(중복포함) 92.1분 (82.6%) / union(무음 제거) 86.3분 (77.4%)
```

발화 구간만 잘라 저장해도 **22%밖에 못 줄인다**. 통화가 짧고(중앙 60초) 발화가 촘촘해서 무음이 별로 없다.

→ 용량 지렛대는 자르기가 아니라 **통화 수를 줄이는 것**. 대분류·성별·증상 유무로 층화 샘플링해서 서브셋을 만드는 게 맞다.

## 3. Mission 1 — 성별 (Accuracy)

```
통화 단위 gender: M 72 / F 28
→ majority baseline accuracy = 72.0%

발화 단위 (gender, speaker): (M,0) 822, (M,1) 890, (F,0) 343, (F,1) 379
→ 전체 발화의 47.9%가 수보자(speaker=0) 발화
```

- 샘플의 72:28은 문서의 전체 통계(M 52.1 / F 47.9)와 크게 다르다. 100건 표본오차일 수도, 서울 편향일 수도 있다. **전체 Training으로 반드시 재측정.** majority baseline이 몇 %인지가 곧 최저 목표선이다.
- 전체 발화의 절반이 수보자 발화다. 제출 CSV가 `[audio file name], [startAt], [endAt], [gender]`라 **채점 단위가 발화 조각으로 확정됐다.** 즉 **이 절반은 "수보자 목소리인데 정답은 신고자 성별"** 이 된다. 학습 때만 speaker를 열어준 규칙과 정확히 맞물린다. 신고자 발화만 골라 학습하고, 추론 때는 어느 조각이 신고자인지 모르는 채로 통화 단위 성별을 내야 하는 구조로 읽힌다.
- 신고자 발화 길이(ms): p10 528 / 중앙 1,680 / p90 5,270

## 4. Mission 2 — 화자 분류 (Accuracy)

### 극성: 문서 정의가 맞다 (앞선 우려 철회)

```
'119/상황실' 언급 발화:  speaker 0 → 115,  speaker 1 → 13
물음표로 끝나는 발화:    speaker 0 → 589,  speaker 1 → 100
통화 첫 발화 실제 텍스트: [0] "네, 119입니다, 말씀하세요." / [0] "예 119입니다." ...
```

**speaker 0 = 수보자(119대원), 1 = 신고자**가 맞다. 활용 가이드라인 문서의 예시 JSON이 잘못 실린 것. 멘토에게 물어볼 필요 없음.

### 난이도를 결정하는 세 가지

```
발화 수 2,434 (speaker 0: 1,165 / 1: 1,269)
길이(ms)  speaker0: p10 661  중앙 1,775  p90 4,342
          speaker1: p10 528  중앙 1,680  p90 5,270
```

1. **길이 분포가 거의 같다.** 길이 feature는 사실상 무의미.
2. **짧은 조각이 지배적이다.** 1초 미만 660개(27.1%), 0.7초 미만 381개(15.7%), 0.5초 미만 172개(7.1%).
   0.7초 미만 조각의 내용 상위: `네.`(96) `예.`(51) `예`(29) `네`(21) `예, 예.`(14).
   텍스트도 순서도 못 쓰니 **0.5초짜리 "네."를 순수 음향만으로 화자 판정**해야 한다. 여기가 accuracy 상한을 정한다.
   → 제출 전에 **길이 구간별 accuracy를 반드시 나눠서 볼 것.** 전체 평균만 보면 어디서 지고 있는지 안 보인다.
3. **인접 발화 겹침 24.9%** (581/2,334). startAt~endAt으로 그대로 자르면 조각의 1/4에 두 화자 목소리가 섞인다. 이건 제거 불가능한 라벨 노이즈다. 겹침 처리 방침(그대로 둘지, 겹친 구간을 잘라낼지)을 정해야 하고, "샘플마다 label에 따라 다른 전처리 금지" 규칙에 걸리지 않게 **라벨을 보지 않고** 결정해야 한다.

### 순서 금지 규칙이 왜 있는지

```
완전 교대 통화: 19/100     ← 홀짝 규칙은 애초에 안 통함
첫 발화 speaker: {0: 68, 1: 32}  ← 위치는 강한 leak
```

같은 화자가 연속으로 말하는 통화가 81%다. 반면 첫 발화는 68%가 수보자이고 대개 "119입니다"로 시작한다. 위치 정보를 쓰면 부당하게 유리해지므로 금지된 것.

### 채널 누수 — 주파수 특징을 쓰기 전에 읽을 것

고역 에너지비(2.2–3.6kHz ÷ 0.3–2kHz) 하나로 임계값만 그어도 **정확도 70.1%**가 나온다. 그런데 이 특징이 보는 건 목소리가 아니라 녹음 경로다(신고자 남녀 차이 0.5dB, 무음 프레임만으로도 57.7%).

→ 상세 근거와 대응 방침: **[docs/mission2_speaker_spectrum.md](docs/mission2_speaker_spectrum.md)**

## 5. Mission 3 — 증상 (클래스별 F1 평균) : 승부처

### 라벨 실태

```
원본 symptom 종류 28개 / 토큰 114개
상위: 기타통증 20, 기타 11, ★열상 9, ★어지러움 7, 찰과상 7, 타박상 6, 요통 6,
      ★호흡곤란 5, ★구토 4, ★두통 4, 그밖의출혈 4, ★전신쇠약 3, ★복통 3, 골절 3 ...

9개 타깃 필터 후: 토큰 39/114 (34.2%)만 생존
  고열 2 / 구토 4 / 두통 4 / 복통 3 / 어지러움 7 / 열상 9 / 오심 2 / 전신쇠약 3 / 호흡곤란 5
  라벨 개수 분포: 0개 70건, 1개 23건, 2개 5건, 3개 2건
```

- **9개 타깃은 전체 증상 토큰의 34%뿐.** 나머지 66%(기타통증, 찰과상, 타박상, 요통 등)는 전부 버려진다.
- **100건 중 70건이 빈 리스트.** 극도로 희소한 멀티라벨 문제다.

### 전략적 함의

클래스별 F1을 평균내는 방식(macro)이면 **희귀 클래스 1개 = 흔한 클래스 1개**다.

- 한 클래스에서 F1=0이 나오면 그 자체로 1/9 = **0.111**을 통째로 잃는다.
- 3개 클래스만 F1 0.4를 내고 6개가 0이면 → 0.133
- 9개 전부 F1 0.2를 내면 → **0.200**

**고르게 조금씩 맞히는 쪽이 이긴다.** 흔한 클래스(열상, 어지러움)만 잘 잡는 모델은 여기서 무조건 진다. 클래스별 threshold 튜닝이 곧 점수인데, Validation 라벨을 보고 맞추면 규칙 위반 소지가 있으니 **Training 내부 split으로 정해야 한다.**

### 베이스라인과 상한

```
키워드 매칭 macro-F1 = 0.182   ← 출발선
  고열 0.200 / 구토 0.400 / 두통 0.000 / 복통 0.000 / 어지러움 0.364
  열상 0.364 / 오심 0.000 / 전신쇠약 0.000 / 호흡곤란 0.308
```

```
정답 symptom 단어가 전사에 문자 그대로 등장: 4/39 (10%)
```

**이게 이번 EDA에서 가장 중요한 숫자다.** 정답의 90%는 전사에 그 단어가 아예 없다. 실제 예시:

| 정답 | 전사 내용 |
|---|---|
| 고열 | "아버님이 119 오지 말라고 하시는데요... 어머니 상태가 너무 안 좋으세요" |
| 복통, 구토 | "우리 애가 많이 아파요... 어제 취했다는데 정신을 못 차리네요" |
| 두통 | (코엑스 사거리 교통사고 신고 대화. 두통 언급 없음) |
| 전신쇠약 | "아까 신고한 사람인데 저는 지금 집에 갈려고 버스 탔거든요" |

두 가지가 동시에 참이다.

1. **어휘 매칭으로는 절대 못 푼다.** "정신을 못 차리네요" → 복통·구토처럼 의미 추론이 필요하다. 이게 왜 언어모델이 필요한지에 대한 근거이고, PPT의 핵심 스토리가 된다.
2. **동시에 라벨-전사 연결이 근본적으로 약하다.** symptom은 수보자가 별도 접수 시스템에 입력한 값이지 통화 내용의 요약이 아니다. 두통 사례처럼 전사에 근거가 아예 없는 경우가 있다. **절대 성능이 낮게 나오는 게 정상이다.** 순위 싸움이라는 점을 기억할 것.

증상이 있는 통화의 대분류는 구급 26 / 구조 4, 화재·기타는 0. 단 `disasterLarge`를 입력으로 쓰는 건 "전사 텍스트 외 라벨링데이터 사용 불가"라 금지. 텍스트로 구급 여부를 먼저 판단하는 2단계 구조는 가능하다.

## 6. 전사 텍스트 품질

```
{중괄호} 0건 / (소괄호) 0건 / 별표 0건 / 영문 27건(GS, KT, HDC 등) / 숫자3자리+ 125건
```

- **마스킹 기호가 전혀 없다.** 주소, 상호명, 지명이 원문 그대로 들어있다. 발표자료에 원문을 인용할 때 주의.
- 구어체, 반복, 말끊김이 많다("예, 의식 아, 그냥 예, 제 의식은 오락가락 하시는 거 같고"). 주최측이 KcELECTRA를 언급한 이유가 여기 있다. 댓글 코퍼스로 사전학습돼서 비정형 구어에 강하다.

## 7. AI Hub 공개 모델과의 관계

공개된 4개 모델(구급/비구급 분류 89.49%, 멀티모달 91.13%, STT CER<10, 16종 분류 F1 90+)은 **우리 미션 3개와 전부 다른 과제다.** 성별·화자·증상은 그중 어느 것도 아니다.

→ PPT에 "기존 벤치마크 91%"를 비교 대상으로 쓰면 틀린다.

다만 세 가지는 가져올 수 있다.

1. KcELECTRA가 이 데이터의 구어체 전사에 잘 맞는다는 게 이미 검증됐다 → Mission 3 백본 1순위.
2. AST(MFCC)를 음성 쪽에 썼다 → Mission 1/2 백본 후보. 단 8kHz→16kHz resample 이슈 필수 처리.
3. 멀티모달이 텍스트 단독보다 **+1.64%p**밖에 못 올렸다(89.49 → 91.13). 이 데이터에서 음성이 주는 추가 정보가 생각보다 적다는 뜻이다. Mission 3에 음성을 못 쓰는 건 손해가 크지 않고, 반대로 Mission 1/2는 음성만으로 풀어야 하니 난이도가 있다.

## 8. 확정된 제약: 중간 점수를 못 본다

**예선은 한 번 제출로 끝이고, 중간에 점수를 볼 수 없다.** 리더보드가 없다.
Validation 폴더는 학습에도 못 쓴다. 즉 **제출 전까지 우리 성능을 알 방법이 자체 검증밖에 없다.**

이 제약이 설계에 미치는 영향이 크다.

**1. Training(서울)에서 자체 held-out을 떼어내야 한다.** 이게 유일한 나침반이다. 지금 데이터 파이프라인 짤 때부터 반영해야 하고, 나중에 붙이면 재작업이다.

**2. Mission 3의 클래스별 threshold가 가장 위험하다.** macro-F1은 threshold에 민감한데 Validation으로 맞출 수 없다. 게다가 희귀 클래스는 추정 자체가 불안정하다 (샘플 기준 고열 2건/100, 오심 2건/100).
→ 단일 split으로 threshold를 정하면 안 된다. **K-fold로 정하고 fold 간 분산을 반드시 확인할 것.** 분산이 크면 그 클래스는 threshold를 보수적으로 잡는 게 낫다.

**3. 도메인 시프트를 한 번도 못 재보고 제출하게 된다.** Training이 서울만인데 Validation 지역 구성을 모른다.
→ 서울 데이터를 신고접수일이나 자치구로 쪼개서 "학습에서 본 적 없는 분포"에 대한 일반화 성능을 미리 재두는 게 안전하다. 랜덤 split만 하면 실제보다 성능이 낙관적으로 나온다.

**4. 포맷 사고가 곧 0점이다.** 점수를 못 보니 CSV 컬럼이 틀려도 알 방법이 없다. 게다가 평가는 아래 명령 **1회 실행**으로 끝나야 한다.

```
python inference.py --audio_dir {wav folder} --label_dir {json folder} --ckpt_path {checkpoint file} --output ./outputs/mission{미션번호}.csv
```

| 미션 | 출력 CSV 컬럼 |
|---|---|
| 1 | `[audio file name], [startAt], [endAt], [gender]` |
| 2 | `[audio file name], [startAt], [endAt], [speaker]` |
| 3 | `[label file name], [symptom]` (string type, 0~9개) |

→ 제출 전에 `inference.py`를 **Validation 폴더에 실제로 돌려서** (라벨은 안 보고) 출력 행 수, 컬럼, 결측, 파일명 매칭을 눈으로 확인할 것. 이건 규칙 위반이 아니다. 학습에 안 쓰는 것뿐이다.

**5. 과감한 베팅보다 앙상블과 보수적 선택이 유리하다.** 피드백 루프가 없으면 도박을 검증할 방법이 없다.

## 9. 멘토 질문

규칙 확인은 사무국/Q&A 채널로 돌리고, 멘토링 50분은 판단이 필요한 것에 쓴다.

### 1순위 — Mission 2 화자 클러스터링 허용 여부

Mission 2는 사실상 **화자 분할(speaker diarization)** 문제다. 표준 해법은 발화별 화자 임베딩 추출 → 통화 내 2그룹 클러스터링 → 각 그룹을 대원/신고자로 판정이다. 규칙은 "순서 사용 불가"만 막았고 클러스터링은 언급이 없다.

- **허용이면**: 표준 diarization 파이프라인. 0.4초짜리 "네."도 같은 통화의 긴 발화들과 목소리를 비교해 판정할 수 있어 짧은 조각 문제(전체의 27%)가 상당 부분 해소된다.
- **금지면**: 발화 하나만 보고 절대 판정. 완전히 다른 모델이 필요하다.

> Mission 2를 화자 분할 문제로 보고, 한 통화 안 발화들의 음성 임베딩을 뽑아 2개 그룹으로 클러스터링한 뒤 각 그룹을 대원/신고자로 판정하려고 합니다. "순서 사용 불가"는 지킬 수 있는데, 같은 통화의 다른 발화와 목소리를 비교하는 것 자체가 금지인가요?

### 2순위 — 자체 validation을 어떻게 만들어야 하나

중간 점수를 못 보니 자체 held-out이 유일한 지표인데, 그게 실제 Validation과 어긋나면 제출 당일에야 안다.

> 예선은 중간 점수를 볼 수 없어서 Training(서울)에서 뗀 자체 held-out이 유일한 나침반입니다. 랜덤 split으로 하면 실제 Validation 성능을 낙관적으로 볼 것 같은데, 시간 기준이나 지역 기준으로 나누는 게 나을까요? Mission 3의 클래스별 threshold를 특히 어디서 정해야 안전할지 조언 부탁드립니다.

### 3순위 — Colab Pro로 어디까지 현실적인가

서울 Training이 10만 건, 110GB 규모다. 여기서 틀리면 한 달을 날린다.

> 세 미션을 Colab Pro 안에서 다 돌려야 하는데, 서울 데이터 10만 건 중 미션별로 어느 정도 규모부터 성능이 포화되는지 감을 주실 수 있나요? Wav2Vec2 fine-tuning까지 가는 게 현실적인지, 임베딩 추출 후 경량 분류기로 가는 게 나은지도 궁금합니다.

### 추가 — Mission 2 채널 특성 사용 가능 여부

게시판 문의 초안: [docs/mentoring_draft.md](docs/mentoring_draft.md)

### 사무국 / Q&A 채널로 돌릴 것 (멘토 시간 쓰지 말 것)

- 슬라이드 10의 Mission 3 F1 상세 정의 (자료 배포 예정)
- ~~Mission 1 제출 CSV 행 단위~~ → 브리프에서 `[audio file name], [startAt], [endAt], [gender]`로 확정. 조각마다 한 행이고, 같은 통화의 행에 같은 값을 채우는 건 모델 설계 문제지 규칙 문제가 아님
